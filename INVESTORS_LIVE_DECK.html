Since the last briefFrom one trade to a campaign engine

Gap restoration (the multiplier)

An arbitrage trade converges the pools it trades — after one cycle the window closes and further trades are correctly refused. The new restore.js solver reads each pair's live reserves and computes the exact constant-product swap (0.3% fee, 50%-of-reserve budget) that pushes the venue back to its target price, then executes it through the real router.

Result: 100/100 restores confirmed, prices landing on 1000.0 / 920.0 every single cycle.

Holdings snapshots

Wallet ETH, GTT, WETH and the engine's profit balance are snapshotted at baseline, before and after every send, and at the end — 102 snapshots. Total spend and profit are derived from first/last snapshots and cross-checked against gas receipts.

Result: snapshot-derived ETH spend equals trade+restore gas to the wei (0.076319208).

Hurdle recording

Every operational obstacle — ambiguous RPC errors, failed restores, aborted cycles, ledger retries — becomes a first-class hurdle entry with its resolution. The campaign runs through problems and leaves receipts instead of stack traces.

Result: 0 hurdles in the campaign window — the log proves it, it isn't an assumption.

Quality bar held throughout

  • The restore solver is a pure function with 6 dedicated unit tests; the suite grew 68 → 74, all green, with the original 68 untouched.
  • A local campaign rehearsal (mock market) proved the loop end-to-end before any gas was spent; the unmodified default path still books its 11.5 mWETH exactly as before.
  • The first live smoke caught a real bug in the solver (inverted pool mechanics) — the safety gates refused every send, 0 transactions were spent, the fix was verified against real pools before the campaign launched. Details on slide 9.

Gate 4 refused correctly — twice a cycle

The campaign's 2 dry cycles hit a converged market and were refused with zero sends — the same refusal logic that protects capital on mainnet. Gates run before anything is paid for.

Gate 5 has teeth

Every send was preceded by an eth_call static-simulation of the exact transaction against current state. A revert there means nothing is broadcast — you can't pay gas for a trade the chain says will fail.

Gate 6 re-checks inside the callback

The engine requires balance ≥ amount + premium + minProfit inside the Aave callback and reverts the whole loan otherwise. Even a scanner bug or state race cannot settle a losing trade.

The multiplierThe gap-restoration engine

One price dislocation → fifty trades

The market was seeded with a deliberate gap: 1000 vs 920 GTT per WETH (8.7%). After each trade the pools converge and the scanner correctly refuses — so the harness re-creates the gap between cycles using real constant-product swaps:

PhaseResult
Restore swaps executed100 (2 per cycle)
Prices landed on target1000.0 / 920.0 — every cycle
Skipped / capped / failed0 / 0 / 0
Restore gas (100 txs)29,084,456,000,000,000 wei
Dry cycles correctly refused2 / 2 (converged market)

The solver is a pure function — given pool reserves and a target price it returns the swap that reaches it, respecting the 0.3% LP fee, refusing unreachable targets instead of guessing. Six unit tests pin the mechanics.

Disclosed in full: restoration is a deliberate loss

Pushing a pool away from equilibrium costs fees and price impact — the restores (and the gas above) are the cost of demonstrating repeated arbitrage on a self-seeded test market. They are accounted separately from the arb's own economics and are not a production cost: real venues re-dislocate on their own, which is exactly the edge a production scanner harvests.

Why this is the interesting IP

  • Closed-loop control: read reserves → solve → swap → verify price → trade. The system verifies its own preconditions before risking anything.
  • Exactness: restores landed on target to four significant figures across 100 independent swaps — the math and the execution agree.
  • Turns a demo into a stress test: 50 repetitions exercise quoting, gating, simulation, sending, confirmation and recording at a cadence no single trade ever could.

We even documented the accounting trap

The profit field of FlashLoanExecuted is the engine's whole post-trade balance, not the per-trade delta — naively summing the 50 events yields 97,760,859,690,363,821 (a sum of running balances). Honest economicsWhy the net is negative — and why that's the point

The two knobs we relaxed (deliberately, and disclosed)

  • Gas floor = 0: the off-chain gate priced gas from live feeData (~17–31 wei/gas) while the sender paid the harness's flat 2 gwei pin. The scanner therefore believed each trade cost ~0.03 µETH of gas when it truly cost ~944.7 µETH.
  • On-chain net guard off: the engine's minProfit enforced only the gross floor (0), not a gas-inclusive net floor.
  • Everything else stayed on and unmodified: cycle validation, live quoting, gross gate, slippage pins, deadlines, the exact-tx simulation, the engine's atomic revert, owner-only withdrawal.

This deliberately recreates October 18's finding F1 — a trade that is gross-profitable but gas-negative — 50 times over, so the economics are measured on live transactions instead of asserted.

Same system, unrelaxed, was proven separately

  • With the gates at production defaults (2 gwei floor + on-chain net guard), the same pipeline refuses exactly these cycles at evaluation time — verified in regression tests and a forced-floor rerun (0 sent, exit 0).
  • The local rehearsal books its 11.5 mWETH with the net guard active — positive-net behavior is demonstrated, not just claimed.

The path to positive net is arithmetic, not hope

  • The arb edge per trade was stable at 3.69% (spread < 0.34% over 50 repetitions) — the strategy works.
  • Gas per transaction is fixed: break-even needs ≈ 0.026 WETH notional (trade gas) — 13× the demo size, and test pools were seeded at 0.1 WETH on purpose.
  • Real production venues re-dislocate continuously — no restore cost needed; that loss exists only because we manufactured the gap on demand.

ResilienceThe bug the tool caught on itself — and the perfect run that followed

Pre-campaign smoke: caught before spending anything

  • The first live smoke found a real bug in the new restore solver: pool mechanics inverted (swapping into a pool grows its input-token reserve), so restores pushed prices 961 → 924 instead of → 1000.
  • The safety gates saw no gap and refused every send — 0 transactions spent. The failure mode of this system is not trading.
  • Fixed at the root in restore.js, unit tests corrected to real constant-product mechanics, then a second live smoke verified restores landing exactly on target plus one confirmed trade — before committing to 50 cycles.

Campaign window: 150 transactions, zero incidents

100/100RESTORES CONFIRMED
50/50SENDS CONFIRMED
0HURDLE ENTRIES

The append-only log contains no error, retry, refusal or recovery entry inside the window — every transaction confirmed on first attempt. Avg confirmation 9.4 s; ~36 s wall per full cycle; 31 minutes end-to-end.

Armed and waiting (F3 hardening)

  • Effect-verified sends: public RPCs can error after accepting a tx ("replacement underpriced"). sendWait checks the transaction's on-chain effect before ever re-sending — a double-spend is structurally impossible.
  • Hurdle ledger: any ambiguity becomes a recorded entry with resolution — the 0 above is an observed fact from the log, not an absence of evidence.
  • Ledger retries with graceful degradation for lagging eth_getLogs nodes; resume support so an interrupted run never re-deploys or double-seeds.
  • Abort guard: if a restore fails, subsequent cycles refuse (and record the refusal) rather than trading into a market the system can't verify.

Design philosophy: every failure path ends in "don't trade" — the only way this system loses money is by paying gas to be told no.
